# 注册功能数据库升级说明

> 提交人：成员 3  
> 配合的接口：`POST /api/register`（已实现，保存方式与现有 `db.verify_password` 配套的 werkzeug 哈希）  
> 字段当前状态：`app_user.password_hash CHAR(60) NOT NULL`  
> 需要的升级：`password_hash` 改为 `VARCHAR(255) NOT NULL`

## 为什么要改

新注册流程使用 `werkzeug.security.generate_password_hash` 生成的口令哈希（与现有 `verify_password` / `check_password_hash` 严格配套，避免出现“注册时一种算法、登录时又换另一种”导致老账号登不上的情况）。

werkzeug 哈希（pbkdf2/scrypt 格式）长度约 100+ 字符，超过现有 `CHAR(60)` 限制，会出现 `Data too long for column 'password_hash'`：

- 在 MySQL 严格模式下：直接报错，注册失败；
- 在非严格模式下：会被截断到 60 字符，登录时校验不通过，且数据被静默破坏。

`admin.password_hash` 当前为 `CHAR(60)`，但本轮只在 `app_user` 表写入真实哈希；如未来成员 1 也为管理员改用 werkzeug 哈希，建议一并升级。**本轮最小改动是 `app_user` 这一列**。

## 升级 SQL（任选其一）

```sql
-- 最小：仅升级 app_user
ALTER TABLE app_user MODIFY COLUMN password_hash VARCHAR(255) NOT NULL COMMENT '口令哈希(werkzeug)';

-- 顺手把 admin 也升级（推荐，避免后续改造时再次迁移）
ALTER TABLE admin MODIFY COLUMN password_hash VARCHAR(255) NOT NULL COMMENT '口令哈希(werkzeug)';
```

执行前建议：

1. 先备份数据库：`mysqldump -u root -p ticket_db > backup_before_register_$(date +%F).sql`
2. 升级字段后再部署新的后端代码（带 `/api/register` 的版本）。
3. 旧的演示账号用 bcrypt 占位串（约 60 字符）仍能登录（`PLACEHOLDER_HASH` 分支兼容 123456）。

## 升级失败 / 出现 Data too long 时怎么办

如果在你升级之前有人尝试注册，后端会捕获 `pymysql.err.DataError` 并返回：

```
注册失败：数据库 password_hash 字段长度不足，
请联系管理员按 docs/注册功能数据库升级说明.md 执行升级
```

请按上面 SQL 升级后重试。
