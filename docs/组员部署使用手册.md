# 组员部署使用手册（在自己电脑上运行演出门票销售系统）

本手册指导组员在一台新电脑上把系统跑起来，或对已有本地环境进行升级。系统由 **MySQL 8.0 数据库 + Flask REST API 后端 + Vue 3 前端静态托管** 构成。

---

## 一、环境准备

| 软件 | 版本要求 | 说明 |
|---|---|---|
| **MySQL** | **8.0**（必须 8.0） | 数据库。安装时请记住设置的 **root 密码** |
| **Python** | **3.8 或以上** | 运行网站后端及数据脚本（安装时勾选 Add to PATH） |
| **Node.js** | **v18+ (可选)** | 仅当需要二次开发或修改前端代码并重新打包时需要 |
| **Navicat** | 任意版本（可选） | 用于可视化查看数据与执行 SQL |

---

## 二、首次安装：全新建库与初始数据导入

如果是首次在电脑上部署，按以下步骤初始化：

1. **确认 MySQL 服务已运行**（Windows 服务中 `MySQL80` 为“正在运行”状态）。
2. **建库与建表**：
   - 打开 Navicat 或终端连接 MySQL；
   - 执行 `sql/schema/ddl.sql`（包含 16 张核心表、外键约束、触发器及核心视图）；
3. **导入基础种子数据**：
   - 执行 `sql/seed/seed_data.sql`（导入 8 场核心演出、基础场次、票档、演示账号及状态自动推进事件 `ev_session_status`）。
4. **开启 MySQL 定时调度器（必须）**：
   在 MySQL 中执行：
   ```sql
   SET GLOBAL event_scheduler = ON;
   ```
   > **说明**：MySQL 默认可能关闭事件调度器。开启后，系统事件 `ev_session_status` 每 1 分钟自动扫描并推进场次状态（从预售到开售、售罄、结束）。同时后端应用层在每次访问列表/详情时也会即时触发状态更新，双保险保证状态无延迟。

## 三、旧库升级步骤（已有数据库无需重新建库）

执行 `sql/migrations/20261016_integrate_members.sql`。可在 Navicat 中打开并执行该文件，或从项目根目录进入 MySQL 客户端后执行：

```sql
SOURCE sql/migrations/20261016_integrate_members.sql;
```

升级会扩容两个密码字段、统一订单视图、补齐已支付订单直接插入及状态变为已支付的销售汇总触发器，并把场次状态事件统一为每 1 分钟执行。还会修正原始演示订单 `NO20250103001` 的两条观演人归属：在下单账号中保存同姓名、同证件的资料并重新关联，保留乘客身份、票价、金额和付款时间。该文件可以重复执行，不清空订单、票档、地址或观演人。

状态按每个场次自己的开售时间和库存计算，同一巡演可以同时有多个城市在售。已结束优先于售罄，售罄优先于预售和在售。旧库和新库使用相同的规则。

升级后检查实际配置：

```sql
SHOW EVENTS;
SHOW TRIGGERS WHERE `Table` = 'ticket_order';
SHOW COLUMNS FROM v_order_detail;
```

正常应有 `trg_order_paid` 和 `trg_order_paid_insert` 两个触发器、17 个订单视图字段，以及每 1 分钟执行的 `ev_session_status`。无网页请求时最多等待约 1 分钟；浏览列表和详情时也会即时刷新状态。

## 四、配置数据库连接并启动后端

1. **设置数据库密码**：
   `backend/config.py` 默认读取环境变量 `DB_PASSWORD`，若未设置则使用默认密码。
   推荐在启动前通过 PowerShell 设置：
   ```powershell
   $env:DB_PASSWORD = '你的MySQL密码'
   ```
2. **安装依赖并启动**：
   ```powershell
   cd c:\Users\Mild\Desktop\db_homework-1\backend
   pip install -r requirements.txt
   python app.py
   ```
3. **访问网站**：
   浏览器访问：**`http://127.0.0.1:5000/app/`**（根路径 `/` 自动跳转至 `/app/`）。

## 五、测试数据生成与一致性自检

为保证全组演练效果和图表展示，本项目配套了完善的数据生成与检验工具：

### 5.1 生成中等规模演示数据（推荐演示使用）
在项目根目录运行：
```powershell
python scripts\data\gen_more_data.py
```
- **生成内容**：35 个城市、44+ 巡演系列、56 个演出、76 个场次、325 个票档、300 个用户及约 1000 笔已支付历史订单。
- **状态分布保障**：严格符合 `售票中 (10%) < 预售中 (30%) < 售罄+已结束 (60%)` 真实分布，各类演出均匀交错。
- **巡演自动聚合**：自动归属城市站点到对应巡演 IP。
- **数据合规**：绝不超卖、绝不超出场馆容量、所有订单付款时间严格位于开售与开演之间。
- **重复运行**：只清理生成器可识别且没有普通订单的演示演出；真实注册用户、管理员新增演出和正常订单保留，已有正常订单的演示演出整体保留。不会按用户 ID 或用户名首字母批量删除账号，也不会把手动新增的独立演出自动归入巡演。因此保留已有业务数据时，数量可能高于上述参考值。
- `gen_full_scale.py` 使用相同的清理规则。生成器用于演示库备数；两个生成器应分别运行。批量重建销售汇总期间暂停网站购票，生成完成后再启动网站。

### 5.2 测试数据异常检查与修复工具
```powershell
# 仅预览不修改数据库
python scripts\data\fix_test_data.py --dry-run

# 执行实际修复
python scripts\data\fix_test_data.py
```
自动检查 5 项指标：
1. 订单付款时间早于开售时间 (`pay_time < sale_start`)；
2. 场次总票数超场馆容量；
3. 演出简介文案清理（自动替换遗留的“压测”词汇为精美简介）；
4. 巡演 series_id 归属完整性；
5. 场次售票状态时间对齐。

### 5.3 自动化功能测试集（76 项回归）
在后端 `app.py` 运行时，在另一终端运行：
```powershell
python scripts\tests\test_api.py
```
覆盖 T1~T14，包含登录注册、巡演与演出详情、限购与购票事务、订单翻页与详情、地址观演人改删保护、管理员场次票档编辑与容量拦截、统计看板图表等 76 项用例。脚本会创建测试资料和订单；最终审查请在数据库副本及独立后端上执行，并通过 `DB_NAME`、`TEST_API_BASE` 指定副本和测试服务。

## 六、前端重新打包（前端二次开发）

如果组员修改了 `frontend/` 中的 Vue 源码，需重新编译成单页静态文件：
```powershell
cd frontend
npm install
npm run build
```
编译产物会自动输出至 `backend/static_web/`，刷新浏览器 `http://127.0.0.1:5000/app/` 即可看到最新效果。

## 七、常见问题与注意事项

1. **开售/预售状态没有变化？**
   - 检查 MySQL 是否开启事件调度器：`SHOW VARIABLES LIKE 'event_scheduler';`，如果为 `OFF` 请执行 `SET GLOBAL event_scheduler = ON;`。
   - 只要用户在网页中浏览或刷新演出，系统应用层也会实时重新计算并纠正当前状态。
2. **为什么修改已售票档的名称会被拒绝？**
   - 业务保护规则：已产生订单的票档**禁止改名**（保持历史订单真实性），但**允许修改后续售价和总票数**（总票数不得低于已售，且所有票档总和不得超场馆容量）。
3. **为什么有的地址或购票人无法修改或删除？**
   - 业务保护规则：为保证历史订单具有法律与审计追溯效力，已被历史订单引用的观演人与收货地址禁止改删，用户可直接新增一条用于后续购票。
